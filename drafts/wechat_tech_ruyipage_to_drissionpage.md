# 我被一个 RangeError 卡了一整天，最后把抓包框架从 ruyiPage 切成了 DrissionPage

前两天我在做一个“机会雷达”小系统。

很简单，就是去某社群的风向标页面，自动翻页，抓列表接口，再把帖子丢给 AI 做筛选、打分，最后只保留真正值得看的机会。

听起来不难。

结果我在“抓响应体”这件事上，硬生生卡了一整天。

不是业务逻辑复杂。

也不是点击路径有多绕。

而是我以为自己遇到的是“脚本小 bug”，最后发现，真正的问题出在**框架底层读响应体的那条链路**。

这篇文章，我就把这个坑完整讲清楚。

如果你也在做浏览器自动化、页面抓包、接口监听，尤其你也碰到过：

- 一拦截页面就白屏
- 明明接口发出去了，但 body 读不到
- 或者直接报一个莫名其妙的 `RangeError: source array is too long`

那这篇你大概率能少踩很多坑。

## 我要做的事情，其实并不复杂

目标页面是某社群里的一个风向标页。

这个页面默认展示热门内容，翻页时会请求一个列表接口。接口返回的是结构化 JSON，每次大概 20 条数据，字段里有标题、正文、标签、评论、图片这些信息。

我的思路很直接：

1. 进入首页
2. 鼠标悬浮到“项目”菜单
3. 点击“风向标”
4. 保持在默认热门页
5. 点击第 2 页，再点回第 1 页
6. 监听列表接口响应
7. 提取关键信息给 AI 分析

路径很像真人操作，理论上比“直接请求业务接口”更稳，也更符合长期自动化的思路。

所以我一开始选的是 `ruyiPage`。

## 一开始，我以为只是我写得不对

最初的现象是这样的：

- 进入页面后，偶尔会像“刷新了一次”
- 开始拦截之后，点到第 2 页，页面直接空白
- 有时候接口像是拦到了，但页面数据没出来
- 有时候页面没白，但一读响应体就报错

最烦的是，这些问题还不是每次都稳定复现。

你会一直处在一种很难受的状态里：

**感觉就差一点点就通了。**

这种坑最折磨人。

因为它不像“语法错了”那样一眼能看出来，也不像“元素定位不到”那样改个 XPath 就结束。

它会让你怀疑所有东西：

- 是不是我翻页动作太快了？
- 是不是登录态不稳？
- 是不是被网站风控了？
- 是不是我没及时放行请求？
- 是不是 body 太大了？

当时我基本把这些可能性都排了一遍。

## 真正让我警觉的是：页面白了，但不是网站自己白的

后来我慢慢发现，这事不太像目标网站的问题。

因为有一个现象特别稳定：

**只要用了响应拦截，如果没有及时 continue，请求就会被挂住。**

页面不是“加载慢”，而是被我自己拦死了。

这个结论一旦确认，方向就变了。

我开始不再纠结页面元素，而是回去看框架源码。

这一步其实特别重要。

很多时候我们用自动化框架，习惯只看表层 API：

- `start_requests()`
- `start_responses()`
- `req.response_body`

感觉这些方法名已经把事情说清楚了。

但真到出问题时，你不看源码，根本不知道它底层到底在干什么。

## 我后来才发现，`req.response_body` 只是“看起来方便”

我往下追了一层，发现 `ruyiPage` 里不管你是：

- 用 `req.response_body`
- 还是用 `listen + collector.get()`

最后都会走到同一个底层调用。

简单说就是：

1. 拦截器或监听器拿到 request id
2. 内部 collector 记录请求
3. 真正读响应体时，再通过底层接口把整包 body 取回来

问题就出在这儿。

因为我碰到的不是“拦不到请求”，而是：

**请求能拦到，但一到“读取完整响应体”这一步，就有概率炸。**

后面报出来的错误也很典型：

`RangeError: source array is too long`

这时候我才真正意识到：

我原来一直想的是：

> “先把完整大对象拿下来，再在 Python 里精简字段不就行了？”

但实际上，这个思路有个前提：

**你得先有能力把完整大对象稳定拿下来。**

而我卡死的地方，恰恰就是这一步。

所以“先拿大对象再精简”的方案，在这里是无效的。

不是精简逻辑写得晚。

而是你根本没稳定跨过“拿大对象”这道门。

## 真正的结论不是“我代码写错了”，而是这条底层链路不适合我当前场景

当时我做了一个很关键的判断：

如果问题出在我自己的业务代码，那我应该能通过这些方式解决：

- 换点击顺序
- 加等待
- 减少重试
- 改成更像真人的交互

但如果这些都做了，问题还是集中出现在“读取响应体”这一步，那我就该怀疑：

**不是我的业务逻辑不对，而是这个框架当前这条取 body 的路径，不适合这个页面。**

这个判断一出来，事情就简单了。

别再死磕了，换方案。

## 我为什么决定切到 DrissionPage

我切框架，不是因为“大家都说它好用”。

而是因为我当时有非常明确的筛选条件：

### 第一，要能稳定监听网络请求

我不想再用那种会把请求流程卡住的拦截方案。

我要的是：

- 不阻塞页面正常加载
- 能等到目标请求完成
- 能把响应体拿回来

### 第二，响应体读取链路要更直接

我不怕 API 丑一点。

我怕的是：

表面上是一个 `response_body`，底下其实绕了三层，再走一个对大响应不稳定的通道。

### 第三，要方便看源码

这点很多人不太重视，但我越来越觉得它很重要。

自动化框架只要不是纯玩具，你迟早会遇到边界问题。

这时候，“能快速看懂它底层怎么实现”，本身就是生产力。

`DrissionPage` 恰好比较符合我这几个条件。

## 真切过去之后，事情一下就顺了

我用 `DrissionPage` 重新做了一版最小验证脚本，只做一件事：

- 从首页进入
- 悬浮“项目”
- 点击“风向标”
- 点到第 2 页
- 再点回第 1 页
- 用 listener 监听目标接口

这次的结果非常直接：

- 第 2 页正常拿到 20 条
- 第 1 页正常拿到 20 条
- 页面没有白
- 没再出现那个 `RangeError`

那一刻其实挺解压的。

因为你终于能确认：

**之前不是你在幻觉里调 bug。**

是真的那条链路不合适。

我后来又继续往 `DrissionPage` 的源码里看了一下，核心点也更让我放心：

它在请求完成后，走的是更直接的响应体读取方式。

对我这个场景来说，这比继续在原来的路径上绕来绕去，靠谱得多。

## 这次踩坑，我最后总结出 4 个经验

### 1. 页面白屏，先怀疑是不是你自己把请求拦死了

很多人一看到白屏，第一反应是：

“网站检测我了。”

有时候确实是。

但也有不少时候，是你自己的拦截逻辑没放行。

这一点一定要先排除。

### 2. 不要只看框架 API 名字，要看它底层怎么拿 body

`response_body` 这个名字很直观。

但直观不代表稳定。

你得知道它到底是：

- 直接从浏览器拿
- 还是绕一圈 collector
- 还是又包了一层事件系统

这对大响应场景影响非常大。

### 3. “先拿大对象再精简”并不总成立

这个思路平时很顺手。

但前提是你能稳定拿到完整 body。

一旦问题就出在“完整 body 取不下来”，那你后面的精简逻辑其实毫无意义。

### 4. 真碰到边界问题，换框架比死磕更便宜

很多技术人都有一个习惯：

已经调到这一步了，再坚持一下，说不定就通了。

但有些坑，本质上不是“再坚持一下”能解决的。

它是底层能力边界。

这种时候，换一个更匹配当前场景的工具，反而是最快的。

## 我现在的做法

我现在已经把这条采集链路默认切到了 `DrissionPage`。

前面的浏览器自动化负责：

- 进入页面
- 模拟真实点击
- 监听接口
- 抽取字段

后面的 AI 流程再负责：

- 去噪
- 需求提炼
- 四维评分
- 只保留真正适合我自己做的机会

这套链路跑通以后，后面的很多事就顺了。

说到底，这次踩坑给我最大的提醒不是：

“哪个框架更牛。”

而是：

**自动化项目里，最值钱的不是你把 API 调通了，而是你知道问题到底卡在业务层、框架层，还是浏览器层。**

一旦这一层分清楚，很多原本看起来很玄学的 bug，其实就没那么玄了。

## 最后一句

如果你最近也在做页面自动化、接口监听或者 AI Agent 工作流，我特别建议你保留一个习惯：

**当你调了半天还是“差一点点”的时候，别急着再补一个 patch。先回去看源码。**

很多时候，真正该改的不是那一行业务代码。

而是你手里那把工具。
